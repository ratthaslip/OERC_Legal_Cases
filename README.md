# OERC_Legal_Cases — OERC Legal and Cases Intelligent Platform (POC)

POC ที่รันได้จริงตาม SDD ครอบคลุม 4 โมดูล

| โมดูล | สิ่งที่พิสูจน์ |
| --- | --- |
| สืบค้นกฎหมายพลังงาน | ตัวบท ณ วันที่ใดก็ได้ (point-in-time), เทียบรุ่น, ค้นภาษาไทยแบบ hybrid, บรรทัดฐานที่อ้างมาตรานั้นตามสิทธิ์ |
| สืบค้นและติดตามงานอุทธรณ์ | อุทธรณ์ (ม.121) และเรื่องร้องเรียน ตามคู่มือ WI-EFL-04: 9 ขั้นพร้อมทางแยก, กรอบเวลาตามกฎหมาย 4 นาฬิกา + กรอบควบคุมภายในรายขั้น (วันทำการ), หนังสือขอข้อมูลพร้อมติดตามกำหนดตอบ |
| สืบค้นงานคดี | ค้นด้วยเลขดำ/แดง ชั้นศาล, กระบวนพิจารณา, โยงกลับเรื่องอุทธรณ์ต้นทาง |
| ระบบช่วยค้นคว้าอัจฉริยะ | RAG ที่กรองสิทธิ์ก่อนค้น, อ้างแหล่งทุกประโยค, ตรวจ citation ก่อนแสดง, ตอบ NO_EVIDENCE เมื่อไม่มีหลักฐาน |

> ⚠ ข้อมูลในชุดนี้เป็นข้อมูลสาธิต (ชุดเดียวกับต้นแบบ UI + เรื่องสมมติที่สร้างเพิ่ม) ไม่ใช่ตัวบทหรือสำนวนจริง

## 1. เริ่มใช้งาน

### แบบ Docker (แนะนำ)

```bash
cp .env.example .env
docker compose up -d --build
docker compose exec api python -m app.seed.seed     # โหลดข้อมูลสาธิต (ล้างฐานทุกครั้งที่รัน)
# เปิด http://localhost:5173  ·  API docs: http://localhost:8000/docs
```

### แบบรันบนเครื่อง

```bash
# backend (Python 3.11+, PostgreSQL 16)
cd backend
pip install -r requirements.txt
export DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/erc
python -m app.seed.seed
uvicorn app.main:app --reload --port 8000

# frontend (Node 20+)
cd frontend && npm install && npm run dev     # http://localhost:5173 (proxy /api → :8000)
```

deploy ชิ้นเดียว: `cd frontend && npm run build` แล้ว FastAPI จะเสิร์ฟหน้าเว็บจาก `frontend/dist` ที่ `http://localhost:8000/` เอง

### เปิดใช้ LLM

| โหมด | ตั้งค่า (.env) | ใช้กับ |
| --- | --- | --- |
| ไม่ใช้ LLM | `LLM_PROVIDER=extractive` (ค่าเริ่มต้น) | สาธิตแบบออฟไลน์: ยกข้อความจากแหล่งมาแสดงพร้อมอ้างอิง |
| GPU ของตัวเอง | `LLM_PROVIDER=openai_compat` `LLM_BASE_URL=http://host.docker.internal:11434/v1` `LLM_MODEL=<ชื่อโมเดล>` | ข้อมูลจริงได้ (ไม่ออกนอกเครื่อง) — Ollama หรือ vLLM |
| Cloud API | `LLM_PROVIDER=anthropic` `LLM_MODEL=claude-sonnet-5-5` `LLM_API_KEY=…` | **ข้อมูลสมมติเท่านั้น** |

Embedding: `EMBED_PROVIDER=hash` (ค่าเริ่มต้น ไม่ต้องมีโมเดล) หรือ `EMBED_PROVIDER=openai_compat` + `EMBED_MODEL=bge-m3` (`ollama pull bge-m3`) — เปลี่ยน embedding แล้วต้องรัน seed หรือ reindex ใหม่

โมเดลภาษาไทยที่ควรนำมาเทียบใน evaluation: Qwen2.5-Instruct, Typhoon (SCB10X), OpenThaiGPT, Llama 3.x — เลือกจากผลกับ golden set ไม่ใช่จากชื่อ

## 2. บทสาธิต (ใช้ตัวสลับบัญชีมุมขวาบน)

1. **ตัวบท ณ วันเกิดเหตุ** — หน้า "สืบค้นกฎหมาย" มาตรา 75 → กด "15 พ.ค. 62" เห็นรุ่นที่ 1, กด "ปัจจุบัน" เห็นรุ่นที่ 2 → เลือกวันที่ก่อนปี 2550 ระบบแจ้ง "ยังไม่มีผลใช้บังคับ" ไม่แสดงรุ่นอื่นแทน
2. **สิทธิ์ต่างกัน ผลต่างกัน** — หน้าอุทธรณ์ ค้น "ท่อส่งก๊าซ ความดัน" ด้วย *นิติกร ข.* เห็น อธ. 42/2566 (ชั้นความลับ) → สลับเป็น *เจ้าหน้าที่ ก.* ไม่เห็นเรื่องนั้น และมีข้อความ "มีอีก N เรื่องอยู่นอกสิทธิ์"
3. **ภาพรวมของ ผอ.คบ.** — สลับเป็น *ผอ.คบ. จ.* เห็นทุกเรื่อง, แถบ 9 ขั้นแสดงจำนวนเรื่องที่ค้างแต่ละขั้น, KPI เกินกรอบ/ใกล้ครบ/รอมอบหมาย
4. **เดินงานตาม WI-EFL-04** — รับเรื่องใหม่ → ผอ.คบ. มอบหมาย → ตรวจสิทธิ/เขตอำนาจ/ระยะเวลา (ระบบคำนวณ 30 วันจากวันได้รับแจ้งคำสั่งเอง) → แจ้งแก้ไขหรือขอข้อเท็จจริง (กำหนดตอบ 7 วัน) → เสนออนุฯ หรือ กกพ. โดยตรง → อนุฯ 30 วัน (ขยายได้ครั้งเดียว ≤30 วัน ต้องแจ้งก่อนครบ) → วาระ → มติ → แจ้งผล (ต้องแจ้งสิทธิฟ้องศาลปกครอง) → ปิดเรื่องเมื่อมีใบตอบรับ
5. **ยื่นพ้นกำหนด** — อธ. 14/2562 ระบบคำนวณว่ายื่นวันที่ 37 จึงรับเรื่องไม่ได้ ต้องเสนอไม่รับพร้อมเหตุผล ข้ามขั้นแสวงหาข้อเท็จจริง
6. **โยงข้ามโมดูล** — จากเรื่องอุทธรณ์ → "ดูตัวบท ณ วันเกิดเหตุ" → จากหน้ามาตรา → เปิดคดีที่อ้างมาตรานั้น → "ดูสำนวนอุทธรณ์ต้นเรื่อง"
7. **ผู้ช่วย** — ถามประเด็น 1 (มาตรา 75) เห็นการอ้าง [S#] ทุกประโยค คลิกไปที่แหล่งได้; ประเด็น 4 (SMR) ได้ "ไม่พบหลักฐาน"; ถามประเด็น 2 ด้วยเจ้าหน้าที่ ก. ไม่มีสำนวนชั้นความลับในแหล่งอ้างอิง
8. **ผู้ใช้ภายนอก** — สลับเป็น *ประชาชนทั่วไป* ใช้ได้เฉพาะกฎหมาย และผู้ช่วยตอบจากตัวบทเท่านั้น

audit log ทั้งหมด (ตรวจ hash chain): `GET /api/v1/audit-events` ด้วยบัญชี *ผู้ดูแลระบบ ง.*

### งานอุทธรณ์ตามคู่มือ WI-EFL-04

| ขั้น | กรอบควบคุมภายใน | สิ่งที่ระบบบังคับ |
| --- | --- | --- |
| 1 รับเรื่อง/มอบหมาย | 1 วันทำการ | มอบหมายได้เฉพาะ ผอ.คบ. |
| 2 ตรวจสิทธิ/เขตอำนาจ/ระยะเวลา/เอกสาร | 3 วันทำการ | ระยะเวลา 30 วันคำนวณจากวันที่ ไม่ให้ติ๊กเอง · ผลตรวจต้องสอดคล้องกับรายการตรวจ · ไม่รับต้องมีเหตุผล |
| 3 แจ้งแก้ไข (ถ้าจำเป็น) | ออกหนังสือ 2 วันทำการ · ตอบ 7 วัน | ต้องมีหนังสืออย่างน้อย 1 ฉบับ |
| 4 แสวงหาข้อเท็จจริง | 7 วันทำการ | หนังสือค้างต้องระบุเหตุผลจึงไปต่อ · ไม่ผ่านอนุฯ ต้องระบุเหตุ |
| 5 คณะอนุกรรมการฯ (ถ้าผ่าน) | 30 วันจากประชุมครั้งแรก | ขยายครั้งเดียว ≤ 30 วัน และแจ้งก่อนครบกำหนด |
| 6 วาระ กกพ. | 3 วันทำการ | — |
| 7 กกพ. วินิจฉัย | 30 วัน (รวมไม่เกิน 90 วัน) | ต้องบันทึกผลตามมติ |
| 8 แจ้งผล | 2–3 วันทำการ | อุทธรณ์ต้องแจ้งสิทธิฟ้องศาลปกครอง |
| 9 ปิดเรื่อง | 2 วันทำการหลังมีหลักฐานการแจ้ง | ต้องมีวันรับหนังสือ (ใบตอบรับ) |

นิยามขั้นตอนอยู่ใน `appeals/workflow.py` และตาราง `workflow_step_def` · วันหยุดราชการโหลดลงตาราง `holiday` (ยังว่าง = นับเฉพาะเสาร์-อาทิตย์)

## 3. โครงสร้าง

```
backend/app
  main.py              FastAPI + problem+json error + เสิร์ฟหน้าเว็บที่ build แล้ว
  auth.py              ผู้ใช้จำลอง (X-Demo-User) ← จุดเดียวที่ต้องเปลี่ยนเป็น OIDC
  authz.py             กฎสิทธิ์ R1, R2, R4 + filter สำหรับการค้น (ตัดสินที่ server)
  audit.py             audit append-only + hash chain + verify_chain()
  schema.sql           ตาราง (ขอบเขตตรงกับ law_db / case_db / ops_db ใน SDD)
  law/                 resolver (point-in-time), router, lookup (อินเทอร์เฟซให้โมดูลอื่น)
  appeals/             workflow.py (9 ขั้น + ทางแยกตาม WI-EFL-04), clocks.py (กรอบเวลาตามกฎหมาย/รายขั้น),
                       service.py (รับเรื่อง มอบหมาย ปิดขั้น หนังสือ ย้อนขั้น), sla.py (วันปฏิทิน/วันทำการ), router
  cases/               router งานคดี
  search/              thai.py (PyThaiNLP), embeddings.py, hybrid.py (FTS + vector + RRF + rerank), indexer.py
  assistant/           rag.py (pipeline), validator.py (ตรวจ citation), llm.py (provider), router (SSE)
  seed/                seed.py (ข้อมูลสาธิต), load_laws.py (นำเข้าตัวบทจริง), prototype_data.json
backend/tests          test_logic.py (ตรรกะล้วน), test_api.py (ผ่าน API + PostgreSQL)
frontend/src           App.jsx (layout ตามต้นแบบ UI), pages/ 4 โมดูล, api.js (รวม SSE client)
```

สถาปัตยกรรม: **modular monolith** — ทุกโมดูลอยู่ใน API เดียว แต่แยก package และไม่ query ตารางของโมดูลอื่นตรง ๆ (เช่น งานอุทธรณ์อ่านชื่อมาตราผ่าน `law/lookup.py`) จึงแยกเป็น service ตาม SDD ได้ภายหลังโดยแก้ที่ขอบเขตเดียว

### ทดสอบ

```bash
cd backend
pytest                                         # ตรรกะล้วน (ไม่ต้องมีฐานข้อมูล)
TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/erc_test pytest   # รวมเทสต์ผ่าน API (ล้างฐานนั้น!)
```

## 4. ส่วนไหนใช้ต่อได้ ส่วนไหนเป็นของสาธิต

| ใช้ต่อได้ (มีเทสต์) | ต้องเปลี่ยนก่อนใช้จริง |
| --- | --- |
| schema, point-in-time resolver, exclusion constraint | ผู้ใช้จำลอง → SSO/AD ผ่าน OIDC (`auth.py`) |
| กฎสิทธิ์ + filter ก่อนค้น, 404 สำหรับเรื่องนอกสิทธิ์ | ข้อมูลสาธิต → ตัวบทจริงที่นิติกรตรวจ (`load_laws.py`) + สำนวนจริง/นิรนาม |
| audit hash chain | cloud LLM → โมเดลบน GPU ภายใน |
| SLA calculator, workflow + optimistic lock | embedding แบบ hash → bge-m3 หรือเทียบเท่า + cross-encoder reranker |
| RAG pipeline, citation validator, NO_EVIDENCE | vector ใน numpy → pgvector/OpenSearch เมื่อข้อมูลเกินหลักหมื่น chunk |
| Thai tokenizer + hybrid search | reindex ทันทีหลังแก้ → outbox + event (SDD 5.4) |

ยังไม่อยู่ใน POC (ตามขอบเขตที่ตกลง): การเปิดชื่อคู่กรณี (party-vault), คิวตรวจทาน Citation, OCR/นำเข้าเอกสาร, แจ้งเตือน, ตั้งค่า/kill switch ผ่านหน้าจอ (ตอนนี้ใช้ `ASSISTANT_ENABLED`)

## 5. แผนถึงกำหนดส่ง มี.ค. 2570

| ช่วง | งาน | ผลลัพธ์ |
| --- | --- | --- |
| ต.ค.–พ.ย. 2569 | รันโครงนี้, คัดตัวบทจริงชุดแรก (พ.ร.บ. 2550 + ระเบียบ/ประกาศที่ใช้บ่อย เลือกมาตราที่มีการแก้ไขจริง), ขอตัวอย่างสำนวนอุทธรณ์/คดี | ตัวบทจริงในระบบผ่าน `load_laws.py` |
| พ.ย.–ธ.ค. 2569 | ติดตั้ง GPU + Ollama/vLLM, ทำสำนวนนิรนาม 30–50 เรื่อง, ร่าง golden set 30 ข้อกับนิติกร | ผู้ช่วยตอบจากข้อมูลจริงบนเครื่องภายใน |
| ม.ค. 2570 | เปลี่ยน embedding + reranker, สคริปต์ evaluation, ปรับ `RAG_MIN_*` จากผล | ตัวเลข recall / citation precision / การรั่วข้ามสิทธิ์ |
| ก.พ. 2570 | ทดสอบกับผู้ใช้ 3 บทบาท, แก้ตาม feedback, load test เบื้องต้น | รายการแก้ไขปิดครบ |
| มี.ค. 2570 | นำเสนอ POC พร้อมรายงานผลเทียบเกณฑ์ผ่าน | เอกสารสรุป POC |

เกณฑ์ผ่านที่ควรตกลงกับ กกพ. ก่อนเริ่ม: golden set ทุกข้อที่ตอบต้องอ้างอิงถูก, ทดสอบเรื่องนอกสิทธิ์รั่ว 0 ครั้ง, คำถามนอกฐานข้อมูลตอบ NO_EVIDENCE ทุกข้อ
