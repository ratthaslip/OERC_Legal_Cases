# OERC_Legal_Cases — OERC Legal and Cases Intelligent Platform (POC)

POC ที่รันได้จริงตาม SDD ครอบคลุม 4 โมดูล

| โมดูล | สิ่งที่พิสูจน์ |
| --- | --- |
| สืบค้นกฎหมายพลังงาน | ตัวบท ณ วันที่ใดก็ได้ (point-in-time), เทียบรุ่น, ค้นภาษาไทยแบบ hybrid, บรรทัดฐานที่อ้างมาตรานั้นตามสิทธิ์ |
| สืบค้นและติดตามงานอุทธรณ์ | อุทธรณ์ (ม.121) และเรื่องร้องเรียน ตามคู่มือ WI-EFL-04: 9 ขั้นพร้อมทางแยก, กรอบเวลาตามกฎหมาย 4 นาฬิกา + กรอบควบคุมภายในรายขั้น (วันทำการ), หนังสือขอข้อมูลพร้อมติดตามกำหนดตอบ |
| สืบค้นงานคดี | ค้นด้วยเลขดำ/แดง ชั้นศาล, กระบวนพิจารณา, โยงกลับเรื่องอุทธรณ์ต้นทาง |
| ระบบช่วยค้นคว้าอัจฉริยะ | RAG ที่กรองสิทธิ์ก่อนค้น, อ้างแหล่งทุกประโยค, ตรวจ citation ก่อนแสดง, ตอบ NO_EVIDENCE เมื่อไม่มีหลักฐาน |

> ⚠ ข้อมูลในชุดนี้เป็นข้อมูลสาธิต (ชุดเดียวกับต้นแบบ UI + เรื่องสมมติที่สร้างเพิ่ม) ไม่ใช่ตัวบทหรือสำนวนจริง

## 1. เริ่มใช้งาน

### แบบ Docker (แนะนำ)

```bash
cp .env.example .env
docker compose up -d --build
docker compose exec api python -m app.seed.seed     # โหลดข้อมูลสาธิต (ล้างฐานทุกครั้งที่รัน — ไม่ทำงานบนระบบจริง)
# เปิด http://localhost:5173  ·  API docs: http://localhost:8000/docs
```

### แบบรันบนเครื่อง

```bash
# backend (Python 3.11+, PostgreSQL 16)
cd backend
pip install -r requirements.txt
export DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/erc
python -m app.seed.seed
uvicorn app.main:app --reload --port 8000

# frontend (Node 20+)
cd frontend && npm install && npm run dev     # http://localhost:5173 (proxy /api → :8000)
```

deploy ชิ้นเดียว: `cd frontend && npm run build` แล้ว FastAPI จะเสิร์ฟหน้าเว็บจาก `frontend/dist` ที่ `http://localhost:8000/` เอง

### ติดตั้งระบบจริง (VM ของสำนักงาน)

```bash
cp .env.example .env        # ตั้ง POSTGRES_PASSWORD, CONFIG_SECRET (openssl rand -hex 32), *_ALLOWED_BASE_URLS, LLM_*
mkdir -p data/raw data/laws-internal data/import data/models && sudo chown -R 10001:10001 data/raw
docker compose -f docker-compose.prod.yml up -d --build          # API ปรับฐานข้อมูลเป็นรุ่นล่าสุดให้เองตอนเริ่ม
docker compose -f docker-compose.prod.yml exec api python -m app.seed.seed --laws-only   # นำเข้าตัวบท + ทะเบียน
```

| เรื่อง | ระบบจริง (`docker-compose.prod.yml`) |
| --- | --- |
| หน้าเว็บ | build เป็นไฟล์ static เสิร์ฟด้วย nginx (ผู้ใช้ไม่ใช่ root) พอร์ต 80 — TLS ที่ WAF ของสำนักงาน หรือเปิด `deploy/nginx/tls.conf` + ใบรับรองใน `deploy/certs/` |
| ความปลอดภัย | header HSTS / CSP / X-Frame-Options, จำกัดคำถามผู้ช่วย AI 6 ครั้งต่อนาทีต่อ IP, ปิด `/docs`, CORS ปิด (โดเมนเดียวกัน) |
| API | ไม่ reload, 1 worker, container อ่านอย่างเดียว (เขียนได้เฉพาะ `data/raw` และ tmp), ผู้ใช้ uid 10001 |
| ฐานข้อมูล | ไม่เปิดพอร์ต; `alembic upgrade head` ทุกครั้งที่ API เริ่ม; ฐานแยกเครื่อง: ตั้ง `EXTERNAL_DATABASE_URL` |
| ข้อมูล | `APP_ENV=production` → `seed` โหมดสาธิตไม่ทำงาน; นำเข้าตัวบท/ทะเบียนรอบใหม่ด้วย `seed --laws-only` (ไม่แตะงานอุทธรณ์ คดี audit log) |
| เริ่มเองหลังรีบูต | `restart: unless-stopped` + health check ทุกบริการ |

**สแกนไวรัสไฟล์อัปโหลด:** บริการ `clamav` (ClamAV) — ไฟล์ต้องผ่านการตรวจชนิดไฟล์จากเนื้อไฟล์ ไม่มี macro/JavaScript ไม่ใช่ zip bomb
ไม่ล็อกรหัส ไม่เกิน `UPLOAD_MAX_PDF_PAGES` หน้า และ clamd ไม่พบมัลแวร์ (`AV_SCAN=required`: clamd ไม่พร้อม = ไม่รับไฟล์) ·
ไฟล์ที่ถูกปฏิเสธไม่ถูกเก็บ และบันทึกใน audit log (`law.upload.reject_file`)

**Log:** JSON บรรทัดละเหตุการณ์ทาง stdout (`docker compose logs api` หรือส่งเข้าระบบรวม log ของสำนักงาน) ทุกบรรทัดมี `request_id`
ตรงกับ header `X-Request-Id` ของคำขอ — ผู้ใช้ที่เจอข้อผิดพลาดเห็นรหัสนี้เพื่อแจ้งผู้ดูแล · access log ไม่บันทึก query string

**Audit log:** ฐานข้อมูลห้ามแก้/ลบ (trigger) และทุกเหตุการณ์ที่ commit ถูกส่งสำเนาไป `AUDIT_SINK`
(ค่าเริ่มระบบจริง: stdout + `data/audit/audit.jsonl` — ควรเป็นดิสก์แยก; เพิ่ม `syslog+tcp://<SIEM>:514` ได้)
ตรวจว่าสำเนาตรงกับฐาน: `docker compose -f docker-compose.prod.yml exec api python -m app.ops audit-verify --file /data/audit/audit.jsonl`
· ฐานข้อมูลแยกเครื่อง: สร้างผู้ใช้ของแอปที่เพิ่ม audit ได้อย่างเดียวด้วย `deploy/db/app-role.sql`

**สำรองและกู้คืน** (`deploy/backup/`):

```bash
openssl rand -base64 32 | sudo tee /root/erc-backup.pass >/dev/null && sudo chmod 600 /root/erc-backup.pass   # เก็บสำเนาไว้นอกเครื่องด้วย
sudo BACKUP_PASSPHRASE_FILE=/root/erc-backup.pass BACKUP_DIR=/mnt/backup/erc deploy/backup/backup.sh       # หรือ systemd timer: erc-backup.timer
sudo BACKUP_PASSPHRASE_FILE=/root/erc-backup.pass deploy/backup/restore.sh /mnt/backup/erc/erc-backup-<เวลา>.tar.enc
docker compose -f docker-compose.prod.yml exec api python -m app.ops check      # จำนวนข้อมูล + ตรวจ hash chain
```

ไฟล์สำรอง 1 ไฟล์ = ฐานข้อมูล (pg_dump) + คลังไฟล์ต้นฉบับ + สำเนา audit log + ตราสารภายใน + `.env` เข้ารหัส AES-256 ·
เก็บ `BACKUP_KEEP_DAYS` วัน (ค่าเริ่ม 30) · restore ตรวจ checksum ก่อนแตะข้อมูล ย้ายไฟล์เดิมไป `*.before-restore-<เวลา>`
และยืนยันว่าจำนวนข้อมูลและ hash ล่าสุดของ audit log ตรงกับตอนสำรอง · CI ทดสอบสำรอง → แก้ข้อมูล → กู้คืน ทุก PR

**แก้โครงสร้างฐานข้อมูล:** แก้ `backend/app/schema.sql` (โครงสร้างล่าสุด) **และ** เพิ่มไฟล์ migration (`cd backend && alembic revision -m "…"`)
— `tests/test_migrations.py` ตรวจว่าสองทางได้ตารางเหมือนกัน

**ไลบรารี:** แก้ช่วงเวอร์ชันใน `backend/requirements.in` แล้วสร้างไฟล์ล็อกใหม่
`uv pip compile requirements.in --python-version 3.12 --generate-hashes -o requirements.txt` (เครื่องมือทดสอบอยู่ใน `requirements-dev.*`)
CI ตรวจช่องโหว่ด้วย pip-audit และ npm audit และทดสอบชุดติดตั้งระบบจริงทั้งชุดทุก PR

### เปิดใช้ LLM

| โหมด | ตั้งค่า (.env) | ใช้กับ |
| --- | --- | --- |
| ไม่ใช้ LLM | `LLM_PROVIDER=extractive` (ค่าเริ่มต้น) | สาธิตแบบออฟไลน์: ยกข้อความจากแหล่งมาแสดงพร้อมอ้างอิง |
| GPU ของตัวเอง | `LLM_PROVIDER=openai_compat` `LLM_BASE_URL=http://host.docker.internal:11434/v1` `LLM_MODEL=<ชื่อโมเดล>` | ข้อมูลจริงได้ (ไม่ออกนอกเครื่อง) — Ollama หรือ vLLM |
| Cloud API | `LLM_PROVIDER=anthropic` `LLM_MODEL=claude-sonnet-5-5` `LLM_API_KEY=…` | **ข้อมูลสมมติเท่านั้น** |

Embedding: `EMBED_PROVIDER=hash` (ค่าเริ่มต้น ไม่ต้องมีโมเดล) หรือ `EMBED_PROVIDER=openai_compat` + `EMBED_MODEL=bge-m3` (`ollama pull bge-m3`) — เปลี่ยน embedding แล้วต้องรัน seed หรือ reindex ใหม่

โมเดลภาษาไทยที่ควรนำมาเทียบใน evaluation: Qwen2.5-Instruct, Typhoon (SCB10X), OpenThaiGPT, Llama 3.x — เลือกจากผลกับ golden set ไม่ใช่จากชื่อ

### โมดูลอุทธรณ์ผูกกับตัวบทจริง (`backend/app/appeals/legal.py`)

- ฐานทางกฎหมายของนาฬิกาและแต่ละขั้นเป็นปุ่มเปิดตัวบท (ณ วันเกิดเหตุ) เช่น ข้อ 19 ระเบียบอุทธรณ์ 2552, ม.45 พ.ร.บ.วิธีปฏิบัติฯ, ม.49 พ.ร.บ.ศาลปกครองฯ
- ฐานการอุทธรณ์ตามข้อ 9 ระเบียบอุทธรณ์ 2552: ม.121/101/106/108–109/113 ยื่นภายใน 30 วัน, ม.105 และ ม.111 ภายใน 60 วัน
- อุทธรณ์คำสั่งพักใช้/เพิกถอนใบอนุญาต (ประกาศ 2555 ข้อ 13–14): ยื่น 30 วัน + นาฬิกาแจ้งคำชี้ขาดภายใน 15 วัน
- เรื่องร้องเรียนของผู้ใช้พลังงาน (ระเบียบ 2553): ไกล่เกลี่ย 30 วัน (ข้อ 16), วินิจฉัย 60 วัน (ข้อ 19), ตรวจข้อ 16/1 (คดีอยู่ในศาล) ตอนตรวจรับ
- รอฝ่ายคดียืนยัน: จุดเริ่มนับ 30 วันของคณะอนุกรรมการฯ (ตัวบท: วันรับอุทธรณ์ / WI: ประชุมครั้งแรก) — ระบบแสดงหมายเหตุในขั้นที่ 5

### ตัวบท พ.ร.บ.การประกอบกิจการพลังงาน พ.ศ. 2550 (ตัวบทจริง)

## 2. บทสาธิต (ใช้ตัวสลับบัญชีมุมขวาบน)

1. **ตัวบท ณ วันเกิดเหตุ** — หน้า "สืบค้นกฎหมาย" เปิดมาตรา 141 → เลือกวันที่ 11 ก.พ. 2560 เห็นรุ่นที่ 1, เลือก 12 ก.พ. 2560 เห็นรุ่นที่ 2 (แก้ไขโดย พ.ร.บ. แก้ไขเพิ่มเติม...ความรับผิดในทางอาญาของผู้แทนนิติบุคคล พ.ศ. 2560) → เลือกวันที่ก่อน 11 ธ.ค. 2550 ระบบแจ้ง "ยังไม่มีผลใช้บังคับ"
2. **สิทธิ์ต่างกัน ผลต่างกัน** — หน้าอุทธรณ์ ค้น "ท่อส่งก๊าซ ความดัน" ด้วย *นิติกร ข.* เห็น อธ. 42/2566 (ชั้นความลับ) → สลับเป็น *เจ้าหน้าที่ ก.* ไม่เห็นเรื่องนั้น และมีข้อความ "มีอีก N เรื่องอยู่นอกสิทธิ์"
3. **ภาพรวมของ ผอ.คบ.** — สลับเป็น *ผอ.คบ. จ.* เห็นทุกเรื่อง, แถบ 9 ขั้นแสดงจำนวนเรื่องที่ค้างแต่ละขั้น, KPI เกินกรอบ/ใกล้ครบ/รอมอบหมาย
4. **เดินงานตาม WI-EFL-04** — รับเรื่องใหม่ → ผอ.คบ. มอบหมาย → ตรวจสิทธิ/เขตอำนาจ/ระยะเวลา (ระบบคำนวณ 30 วันจากวันได้รับแจ้งคำสั่งเอง) → แจ้งแก้ไขหรือขอข้อเท็จจริง (กำหนดตอบ 7 วัน) → เสนออนุฯ หรือ กกพ. โดยตรง → อนุฯ 30 วัน (ขยายได้ครั้งเดียว ≤30 วัน ต้องแจ้งก่อนครบ) → วาระ → มติ → แจ้งผล (ต้องแจ้งสิทธิฟ้องศาลปกครอง) → ปิดเรื่องเมื่อมีใบตอบรับ
5. **ยื่นพ้นกำหนด** — อธ. 14/2562 ระบบคำนวณว่ายื่นวันที่ 37 จึงรับเรื่องไม่ได้ ต้องเสนอไม่รับพร้อมเหตุผล ข้ามขั้นแสวงหาข้อเท็จจริง
6. **โยงข้ามโมดูล** — จากเรื่องอุทธรณ์ → "ดูตัวบท ณ วันเกิดเหตุ" → จากหน้ามาตรา → เปิดคดีที่อ้างมาตรานั้น → "ดูสำนวนอุทธรณ์ต้นเรื่อง"
7. **ผู้ช่วย** — ถามประเด็น 1 (มาตรา 121) เห็นการอ้าง [S#] ทุกประโยค คลิกไปที่แหล่งได้; ประเด็น 4 (SMR) ได้ "ไม่พบหลักฐาน"; ถามประเด็น 2 ด้วยเจ้าหน้าที่ ก. ไม่มีสำนวนชั้นความลับในแหล่งอ้างอิง
8. **ผู้ใช้ภายนอก** — สลับเป็น *ประชาชนทั่วไป* ใช้ได้เฉพาะกฎหมาย และผู้ช่วยตอบจากตัวบทเท่านั้น

audit log ทั้งหมด (ตรวจ hash chain): `GET /api/v1/audit-events` ด้วยบัญชี *ผู้ดูแลระบบ ง.*

## 4. ส่วนไหนใช้ต่อได้ ส่วนไหนเป็นของสาธิต

| ใช้ต่อได้ (มีเทสต์) | ต้องเปลี่ยนก่อนใช้จริง |
| --- | --- |
| schema, point-in-time resolver, exclusion constraint | ผู้ใช้จำลอง → SSO/AD ผ่าน OIDC (`auth.py`) |
| กฎสิทธิ์ + filter ก่อนค้น, 404 สำหรับเรื่องนอกสิทธิ์ | ข้อมูลสาธิต → ตัวบทจริงที่นิติกรตรวจ (`load_laws.py`) + สำนวนจริง/นิรนาม |

| SLA calculator, workflow + optimistic lock | embedding แบบ hash → bge-m3 หรือเทียบเท่า + cross-encoder reranker |

| Thai tokenizer + hybrid search | reindex ทันทีหลังแก้ → outbox + event (SDD 5.4) |

## Reranker และการวัดผลผู้ช่วย AI

ทดลองเปิด cross-encoder reranker (BAAI/bge-reranker-v2-m3) แล้ววัดผลกับชุดคำถามทดสอบ 60 ข้อ:

```bash
# 1) วัดรอบฐาน (ไม่ rerank)
docker compose exec api python -m eval.run_eval --out eval/results_none.json

# 2) เปิด reranker (ครั้งแรกดาวน์โหลดโมเดล ~2.3 GB) แล้วตั้ง .env: RERANK_PROVIDER=tei
docker compose --profile rerank up -d reranker
docker compose logs -f reranker          # รอจนขึ้น "Ready"
docker compose up -d api                 # โหลด .env ใหม่

# 3) วัดอีกรอบแล้วเทียบรายข้อ
docker compose exec api python -m eval.run_eval --out eval/results_tei.json
docker compose exec api python -m eval.compare eval/results_none.json eval/results_tei.json
```

ถ้า image CPU รุ่นใหม่โหลดโมเดลไม่ขึ้น ให้ลอง `RERANK_IMAGE=ghcr.io/huggingface/text-embeddings-inference:cpu-1.4`

### กันคะแนนถอยหลัง (CI)

ทุก PR รัน `.github/workflows/ci.yml`: pytest + ชุดคำถามทดสอบ + build หน้าเว็บ — PR ไม่ผ่านถ้าข้อที่เคยผ่านใน `eval/baseline.json`
กลับไม่ผ่าน CI ไม่มีทะเบียนจริง (ข้อมูลภายใน) จึงรันโหมด `public` ข้ามข้อที่ต้องใช้ทะเบียน บนเซิร์ฟเวอร์ที่นำเข้าทะเบียนแล้วรันโหมด `full`:

```bash
docker compose exec api python -m eval.run_eval --inproc --baseline eval/baseline.json          # เทียบ baseline
docker compose exec api python -m eval.run_eval --inproc --baseline eval/baseline.json --write-baseline  # เมื่อผ่านเพิ่ม
```

## ความสัมพันธ์ระหว่างกฎหมาย (`law_relation`)

ตารางเดียวเก็บทุกเส้น ทิศ src → dst: `authorizes` (มาตราแม่บท → กฎหมายลำดับรอง, จากทะเบียน), `amends` / `repeals`
(จาก relations ในไฟล์ตัวบท), `refers_to` (มาตรา/ข้อที่อ้างถึงกัน สกัดจากถ้อยคำอัตโนมัติ, status `auto`) และ `remedy`
(ช่องทางเยียวยาหลายทอด จากไฟล์ `backend/app/seed/relations/*.json` ที่นิติกรอนุมัติแล้ว — ไฟล์ `*.draft.json` ไม่โหลด)
สร้างใหม่ทุกครั้งที่นำเข้าตัวบทหรือทะเบียน · API: `GET /api/v1/laws/relations?eli=…`, `GET /api/v1/laws/relations/walk?eli=…`
(เดินหลายทอดด้วย recursive CTE เฉพาะเส้นที่อนุมัติแล้ว) · หน้ามาตราแสดงแผง "ความสัมพันธ์กับบทบัญญัติอื่น"

รหัสอ้างอิงระดับวรรค: `…/sec-121/v1#para-4`, `…/sec-11/v1#para-1/item-4` คำนวณจากถ้อยคำ (1 บรรทัด = 1 ย่อหน้า, "(1)" = อนุ)
ผู้ช่วย AI ยกวรรคที่ตรงคำถามและแหล่งที่ส่งให้ LLM มีป้าย `[วรรค…]` กำกับ ตัวตรวจอ้างอิงปฏิเสธประโยคที่อ้างวรรคที่ไม่มีอยู่จริง

## กฎหมายลำดับรองจากฝ่ายกฎหมาย (`backend/app/seed/laws/legal-team/`)

ไฟล์ Word/PDF จากฝ่ายกฎหมาย (Google Drive) แปลงเป็นตัวบทด้วย `backend/tools/legal_import/` (ดู README ในโฟลเดอร์นั้น)
ระบบผูกกับทะเบียนด้วยชื่อตามทะเบียน (`registerTitle`) · ฉบับแก้ไขเชื่อมกับฉบับหลักด้วยเส้น `amends` ระดับตราสาร
และฉบับหลักแสดงคำเตือนจนกว่าจะประกอบตัวบท · ข้อสังเกตจากการแปลงอยู่ในแท็บ "ความครอบคลุมข้อมูล" → ประเด็นรอตรวจ

ตราสารภายใน (`"classification": "internal"` ในไฟล์ JSON — ตั้งให้อัตโนมัติกับหมวด "การบริหารองค์กร": ระเบียบบุคคล
เงินเดือน เครื่องแบบ แบ่งส่วนงาน กฎบัตร ฯลฯ) เห็นเฉพาะบัญชีเจ้าหน้าที่ ทั้งสารบัญ หน้ามาตรา การค้นหา ผู้ช่วย AI และไฟล์ต้นฉบับ
(ไฟล์ที่ผูกกับตราสารภายในถือเป็นไฟล์ภายในแม้เคยเก็บเป็น public) — บัญชีทั่วไปได้ 404 เหมือนไม่มี; ชื่อเรื่องในทะเบียนยังเปิดเผยตามเดิม

การค้นหาเมื่อคลังใหญ่ขึ้น: บทบัญญัติยาว (แนบท้าย/ทั้งฉบับ) แบ่งเป็นท่อน ~900 อักษร · น้ำหนักแหล่ง (`search_chunk.weight`):
พ.ร.บ. 1.15, ระเบียบบริหารภายในสำนักงาน 0.8, แนบท้าย 0.85, แถวทะเบียนที่มีตัวบทแล้ว 0.85 ·
ผู้สมัครชุดที่ 3 จัดอันดับด้วยความครอบคลุมคำถ่วง IDF · `RERANK_PROVIDER=legal` เป็นค่าเริ่มต้น
ไฟล์ต้นฉบับจาก zip: `python -m app.seed.raw_files zip <ไฟล์.zip> … --class public --from "ฝ่ายกฎหมาย"`

## หน้าตั้งค่าระบบ (ผู้ดูแล ADM)

เมนู "ตั้งค่าระบบ" แสดงเฉพาะบัญชีผู้ดูแล: แก้ LLM provider / endpoint / model / API key / timeout ได้โดยไม่ต้อง restart
(มีผลภายใน 10 วินาที) และทดสอบการเชื่อมต่อได้ ค่าเก็บในตาราง `app_setting` ทับค่าจาก `.env` · "กลับไปใช้ค่าจาก .env" ล้างค่าทั้งหมด
- API key เข้ารหัสด้วย `CONFIG_SECRET` (ต้องตั้งใน `.env`) และไม่ส่งกลับหน้าเว็บ — แสดงแค่ 4 ตัวท้าย
- ทุกการแก้/ทดสอบบันทึกใน audit log (ไม่บันทึกค่า key)
- ตัวป้องกัน LLM ภายนอก (ส่งเฉพาะตัวบทสาธารณะ) คำนวณจาก endpoint ที่ใช้จริงเสมอ — ปิดจากหน้าเว็บไม่ได้
- เมื่อเปิดให้ผู้อื่นใช้: ตั้ง `LLM_ALLOWED_BASE_URLS` เพื่อจำกัด endpoint (ระหว่างยังไม่มี SSO บัญชีสาธิตสลับเป็นผู้ดูแลได้)

## คลังคำค้นหา (`backend/app/search/lexicon.json`)

คำย่อ (กกพ., พ.ร.ฎ., กฟผ. …), คำพ้อง และคำเรียกทั่วไป → ถ้อยคำในกฎหมาย ฝ่ายกฎหมายแก้ไฟล์นี้ได้โดยตรงแล้ว index ใหม่
นอกจากนี้ระบบแปลงเลขเป็นคำ ("หกสิบวัน" → 60) และจับคู่คำถามแบบ "กี่วัน / เท่าไร / ใช้บังคับเมื่อใด / มีอะไรบ้าง"
กับถ้อยคำที่ตอบคำถามแบบนั้นโดยอัตโนมัติ

## ไฟล์ต้นฉบับ (PDF ตัวบท, Excel ทะเบียน)

เก็บในโฟลเดอร์ `./data/raw` (เมานต์เป็น `/data/raw` ในคอนเทนเนอร์ ไม่อยู่ใน git) แยก `public/` (ตัวบทกฎหมาย) และ `internal/`
(ทะเบียน, คู่มือภายใน) ชื่อไฟล์คือ SHA-256 ของเนื้อไฟล์ เขียนครั้งเดียวและตั้งเป็นอ่านอย่างเดียว ตาราง `raw_file` เก็บชื่อเดิม แหล่งที่มา
ผู้ส่ง และวันที่รับ ส่วน `sourceFiles` ใน `seed/laws/*.json` บอกว่าตัวบทแต่ละฉบับดึงข้อความมาจากไฟล์ใด (ผูกด้วย hash)

```bash
mkdir -p data/raw data/raw-inbox          # วางไฟล์ + manifest.csv ใน data/raw-inbox
docker compose up -d api
docker compose exec api python -m app.seed.raw_files manifest /data/raw-inbox/manifest.csv --dir /data/raw-inbox
docker compose exec api python -m app.seed.raw_files add /data/raw-inbox/<ไฟล์>.pdf --class internal --source "..."
docker compose exec api python -m app.seed.raw_files verify   # ไฟล์ครบและ hash ตรงทุกไฟล์
```

ทะเบียน Excel ที่นำเข้าจะถูกเก็บสำเนาใน `internal/` ให้อัตโนมัติ · สำรอง `data/raw` พร้อมฐานข้อมูลเสมอ ·
ย้ายไป object storage ภายหลังได้โดยใช้ key เดียวกัน (`{public|internal}/{sha[:2]}/{sha}.ext`)


## ข้อมูลภายในกับเครื่องที่ติดตั้ง

ตราสารภายในของสำนักงาน (ระเบียบบริหารงานภายใน 56 ฉบับ) **ไม่อยู่ใน repo** — ส่งเป็นชุดไฟล์แยก แล้ววางที่ `data/laws-internal/` บนเครื่องของสำนักงานเท่านั้น
(seed นำเข้าให้อัตโนมัติ, `LAWS_INTERNAL_DIR` เปลี่ยนที่อยู่ได้)

เครื่องพัฒนาส่วนตัวหรือบนคลาวด์ให้ตั้ง `PUBLIC_DATA_ONLY=true` ใน `.env`:
- seed ข้ามตราสารภายใน และนำเข้าทะเบียนเฉพาะคอลัมน์ที่ประชาชนเห็น (ไม่เก็บหน่วยงาน หมายเหตุ การทบทวน ไฟล์แนบ ข้อสังเกต และไม่เก็บสำเนาไฟล์ทะเบียน)
- คลังไฟล์ต้นฉบับไม่รับไฟล์ภายใน; หน้านำเข้าเอกสารไม่รับเอกสารภายใน

ล้างข้อมูลภายในที่มีอยู่แล้วบนเครื่อง:
```bash
docker compose up -d api                                         # หลังตั้ง PUBLIC_DATA_ONLY=true
docker compose exec api python -m app.seed.seed                  # ยังใช้ register.xlsx — นำเข้าเฉพาะคอลัมน์สาธารณะ
docker compose exec api python -m app.seed.public_only export-register   # → data/raw/register-public.json
docker compose exec api python -m app.seed.public_only purge     # ดูก่อนว่าจะลบอะไร แล้ว ... purge --yes
shred -u data/register.xlsx                                       # ไฟล์ต้นฉบับมีคอลัมน์ภายใน
docker compose exec api python -m app.seed.seed                  # ใช้ register-public.json แทน
```
